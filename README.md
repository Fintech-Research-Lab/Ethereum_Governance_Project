# Decentralized Crypto Governance? — Reproduction Package

**Paper:** Fracassi, C., Khoja, M., & Schär, F. (2024). *"Decentralized Crypto Governance?
Transparency and Concentration in Ethereum Decision-Making."* SSRN 4691000.
https://papers.ssrn.com/sol3/papers.cfm?abstract_id=4691000

---

## What this is

This repository is a clean, from-scratch, pure-Python (Polars-first) reproduction of the paper's
**entire** published pipeline — raw data through final figures and tables, ported from the original
project (a mix of Stata `.do` files and standalone Python scripts, each hand-run in a specific order
on a specific developer's machine).

Every algorithmic bug found in the original code during conversion has been fixed — this package's
default behavior computes corrected values, not the originally-published ones, in every place a bug
affected a result. Where a fix moves a published number, the original (bug-reproducing) behavior
remains available as an explicit, non-default opt-in on the relevant function, for anyone who wants
to reproduce the published figures/tables exactly as printed; see the Validation section below for
exactly where and by how much numbers move.

Concretely, that means:
- No hardcoded, developer-specific file paths anywhere (the original had three different Box-sync
  paths baked into ~15 scripts, one per developer) — see `code/config.py`.
- Polars instead of pandas for all data loading/transformation/saving (pandas is used only at a few
  explicit, documented library boundaries — e.g. `statsmodels` regressions — and converted back
  immediately).
- One orchestrator, `code/run_pipeline.py`, runs every stage in dependency order in a single
  process, instead of a human manually running ~20 separate Stata/Python scripts in the right
  order.
- Every raw input file is treated as strictly immutable — nothing in `code/` ever writes to
  `data/raw/`.

## Data availability

One category of raw input is **not included in this public repository**, and is listed in
`.gitignore` rather than committed: **Revelio Labs / LinkedIn-derived career data**
(`data/raw/revelio/author_to_revelio_userid.parquet`, `revelio_positions_enriched.parquet`,
`revelio_user.parquet`, `_revelio_input.csv`), used by the labor-market analysis (stage 17,
Table 3 / Figure 4). This is accessed through a WRDS institutional license; redistributing the
underlying vendor data is not permitted by that license, and the seed file (`_revelio_input.csv`)
is a plain-text real-name-to-LinkedIn-URL crosswalk for 491 individuals. The original pull code
(querying `revelio.individual_user`/`individual_positions` tables via WRDS, matching on
`profile_linkedin_url`) is kept privately alongside this package's own development history, not in
this public repo; contact the authors if you have WRDS/Revelio access and want to regenerate it.

Everything else under `data/raw/` is included, including `data/raw/social/linkedin_data.csv` and
`client_employment.csv` (manually collected LinkedIn/employment data, not WRDS-licensed), which
`fig_company_concentration.py` and `fig_client_concentration.py` need for Figure 20's panels a-d.

Without the Revelio data above, `run_pipeline.py` reproduces every figure and table in the current
paper except stage 17 (the labor-market analysis, Table 3 / Figure 4); that output is already
checked in under `paper/latex/` and `output/` so the result remains visible without re-running it.

## Quickstart

```bash
conda env create -f environment.yml
conda activate decentralized-crypto-governance
python code/run_pipeline.py
```

This runs all 17 stages in dependency order and regenerates every intermediate dataset, figure, and
table from `data/raw/` through to `output/figures/` and `output/tables/` (stage 17, the
labor-market analysis, needs the WRDS/Revelio data described in "Data availability" above and will
fail without it — the other 16 stages are unaffected). Useful flags:

- `python code/run_pipeline.py --list` — print all 17 stages (in order) and exit, without running anything.
- `python code/run_pipeline.py --skip-existing` — skip a stage if its expected output file(s) already exist on disk (useful for resuming a partial run).
- `python code/run_pipeline.py --stage <stage_name>` — run just one named stage (see `--list` for valid names), for debugging a single stage in isolation. No dependency ordering is enforced with this flag.

The pipeline stops on the first stage failure by default and always prints a final summary of
which stages succeeded, failed, or were skipped.

## Validation

`python code/run_pipeline.py` has been run end-to-end successfully (stages 1-16; stage 17 needs
WRDS/Revelio access not available in this environment), producing every available figure and table
in `output/`. Cross-checking that output against the paper's own published numbers (as of the
pre-revision SSRN draft this validation pass was run against):

- The headline sample size — **612 EIPs** — reproduces exactly.
- Most figures and tables match the published paper closely: headline author-count statistics
  (roughly **689-698 unique authors**) and FEM engagement statistics (unique users, likes, views,
  replies) match to 2-3 decimal places.
- A small number of figures **deliberately diverge** from the published paper, because a confirmed
  bug behind that published number has since been fixed rather than reproduced. Concretely: the
  "Top Client Developers" percentage now shown in the anonymity figure (78.8% published -> 80.0%
  here), the FEM-forum figure's year-by-year view totals (now Figure 13a), and the
  EIP-authorship-concentration figures (now Figures 8/10/11, which needed a sort-order fix to even
  approach the published values, and now match them closely). Each fix is documented inline in the
  relevant script's docstring with the exact original-vs-fixed numbers, and the original
  (bug-reproducing) behavior remains available as an explicit opt-in for anyone who wants to
  regenerate the published figures exactly as printed.
- The two regression tables this validation pass also checked (FEM-engagement regressions, EIP
  finalization/implementation regressions) have since been dropped from the published paper during
  revision and are no longer part of this package's active pipeline.
